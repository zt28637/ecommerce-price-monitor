## 第 1 章 · 三件必须先懂的事

1. **BI 不存你的业务数据**。Metabase 是"会画图的 SQL 客户端"，每次刷新都去 MySQL 现查现画。所以采集入库后看板自动更新，**不存在"同步到 BI"这一步**。
2. **每张图 = 一段 SQL**。图难看就改 SQL，没有拖拽黑魔法。本教程全部用「原生查询」而非拖拽建模。
3. **两个数据库物理隔离**：业务数据在 MySQL；看板配置（账号、数据源、图、布局）在 Metabase 自己的库（默认 H2 文件）。**删掉看板配置，业务数据一根毛都不动**——这就是敢让人随便试的底气。

### 启动脚本（`F:\Programs\metabase\start_metabase.bat`）

## 第 3 章 · 视图层：本模块唯一的技术含量

### 3.1 为什么必须建视图（不建会让数字"静默出错"）

`price_history` 是 append-only：每跑一次采集追加一批，不覆盖。一天跑 4 次，同一条价格就有 4 行。实测：**1055 行原始数据只对应约 400 个"每 SKU 每天"的组合**。

如果直接拿原始表画"每日均价"：跑得多的那天样本量虚高、均价被重复值拉扯，**图上不报错，但数字是假的**。这是 BI 最危险的一类错。

### 3.2 四个视图各管什么

| 视图 | 职责 | 关键点 |
|------|------|--------|
| `v_price_daily` | 每 SKU 每天只留最后一次采集 | `ROW_NUMBER() OVER (PARTITION BY product_id, sku_name, crawl_date ORDER BY crawl_time DESC, id DESC)`；**第二排序键 `id` 不能省**——同批插入 `crawl_time` 完全相同，不加则取哪条不确定 |
| `v_price_change` | 日快照 + 环比 + 历史最低 | 环比用 `LAG`；历史最低用 `ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING`（**排除当日**，否则「历史新低」恒为空） |
| `v_sku_latest` | 当前三档价 + 折扣率 | **只保留最近采集日**：`competitor_sku` 是 upsert 累积表，下架商品永不删，不过滤会把两个月前的旧价当"现价" |
| `v_shop_summary` | 店铺维度汇总 | 均价/最低/最高/SKU 数 |

DDL：[project/config/init_bi_views.sql](../../config/init_bi_views.sql)，全部 `CREATE OR REPLACE`，**可反复重跑**，不用先 DROP。

### 3.3 口径一致：让看板和钉钉说同一种话

钉钉预警的判定在 `alert.py`，看板的判定在 `v_price_change`。两边定义必须完全一致，否则出现"钉钉说破线了、看板说没破"——这是信任崩塌的开始。

对齐后的统一口径：
- **"上一次价"＝该 SKU 今天之前最近一次采集**（不是日历昨天；断跑几天也跨空窗对齐）
- **"历史最低"＝排除今日的历史最低**
- **"今日"＝`DATE(crawl_time)=今天` 的行**（不是表里所有行）

2026-10-25 实测：修一致口径后，钉钉从 26 条（含两个月前的幽灵降价）收敛到 4 条真实新低，与看板 A7/A8 逐行一致。

1. Metabase → 左上齿轮 → 管理 → Databases → 添加数据库 → MySQL
2. 填写：`price_monitor` / `127.0.0.1` / `3306` / `price_monitor` / 账号密码 / `utf8mb4`

## 第 5 章 · 建 12 张图（逐图：问题 → SQL → 图形）

建图统一路径：「+」→ 问题 → `price_monitor` → 原生查询（`</>`）→ 贴 SQL → 运行 → 选图形 → 保存到集合。

> **中文别名含 `%`/空格/括号必须加反引号**：`` AS `涨跌幅%` ``。

### A1 监控商品数（指标卡）
```sql
SELECT COUNT(DISTINCT product_id) AS `商品数` FROM v_sku_latest
```
### A2 监控 SKU 数（指标卡）
```sql
SELECT COUNT(*) AS `SKU数` FROM v_sku_latest
```
### A3 覆盖店铺数（指标卡）
```sql
SELECT COUNT(DISTINCT shop_name) AS `店铺数` FROM v_sku_latest
```
### A4 已采集天数（指标卡）
```sql
SELECT COUNT(DISTINCT crawl_date) AS `天数` FROM v_price_daily
```
> 指标卡只认 **1 行 1 列**；想要一排 4 个数字就建 4 张卡。

### A5 每日采集量与均价趋势（折线）
```sql
SELECT crawl_date AS `采集日期`,
       ROUND(AVG(price), 2) AS `均价`,
       COUNT(*) AS `当日SKU数`
FROM v_price_daily
GROUP BY crawl_date ORDER BY crawl_date
```
> 点数 = 采集天数。只有 4 个点是数据现状，不是 bug。

### A6 店铺均价 TOP15（横向条形）
```sql
SELECT shop_name AS `店铺`, avg_price AS `均价`, sku_count AS `SKU数`
FROM v_shop_summary
WHERE avg_price IS NOT NULL
ORDER BY avg_price DESC LIMIT 15
```
> **必须横向 + TOP N**：竖向柱状图塞 30+ 个中文店名，每根不到 5px，等于没画。

### A7 降价榜 TOP20（表格）
```sql
SELECT product_name AS `商品`, shop_name AS `店铺`, sku_name AS `SKU`,
       crawl_date AS `日期`, price AS `现价`,
       prev_date AS `上次日期`, prev_price AS `上次价`,
       price_diff AS `涨跌额`, change_pct AS `涨跌幅%`
FROM v_price_change
WHERE price_diff < 0
ORDER BY change_pct ASC LIMIT 20
```
> 带 `上次日期` 是为了防止误读：从 10-08 到 10-25 的降幅不是"昨天降的"。

### A8 历史新低预警（表格，与钉钉同口径）
```sql
SELECT product_name AS `商品`, shop_name AS `店铺`, sku_name AS `SKU`,
       crawl_date AS `日期`, price AS `现价`,
       min_price_before AS `此前历史最低`,
       ROUND(price - min_price_before, 2) AS `再低多少`
FROM v_price_change
WHERE min_price_before IS NOT NULL AND price < min_price_before
ORDER BY price - min_price_before ASC LIMIT 20
```

### A9 价格区间分布（条形）
```sql
SELECT 价格带, COUNT(*) AS `SKU数` FROM (
    SELECT CASE
        WHEN sku_price < 1000 THEN '01. <1000'
        WHEN sku_price < 2000 THEN '02. 1000-2000'
        WHEN sku_price < 3000 THEN '03. 2000-3000'
        WHEN sku_price < 4000 THEN '04. 3000-4000'
        ELSE '05. >=4000' END AS 价格带
    FROM v_sku_latest WHERE sku_price IS NOT NULL
) t GROUP BY 价格带 ORDER BY 价格带
```
> 分桶写死不用自动 binning：跨月可比；前缀 `01.` 保证语义排序。

### A10 折扣力度 TOP20（表格）
```sql
SELECT product_name AS `商品`, shop_name AS `店铺`, sku_name AS `SKU`,
       original_price AS `划线价`, sku_price AS `现价`,
       discount_rate AS `折扣(折)`, crawl_time AS `采集时间`
FROM v_sku_latest
WHERE discount_rate IS NOT NULL AND discount_rate > 0
ORDER BY discount_rate ASC LIMIT 20
```
> `discount_rate` 是"折"（8.5=八五折），视图内 `sku_price/NULLIF(original_price,0)*10` 防除零。

### B1 最新日涨跌幅分布（条形）· 2026-10-25 新增
```sql
SELECT 涨跌区间, COUNT(*) AS `SKU数` FROM (
    SELECT CASE
        WHEN change_pct <= -10 THEN '01. 降价>10%'
        WHEN change_pct < 0 THEN '02. 降价0-10%'
        WHEN change_pct = 0 THEN '03. 持平'
        WHEN change_pct < 10 THEN '04. 涨价0-10%'
        ELSE '05. 涨价>10%' END AS 涨跌区间
    FROM v_price_change
    WHERE crawl_date = (SELECT MAX(crawl_date) FROM v_price_daily)
      AND prev_price IS NOT NULL AND change_pct IS NOT NULL
) t GROUP BY 涨跌区间 ORDER BY 涨跌区间
```

### B2 每日降价 SKU 数（>5%，折线）· 2026-10-25 新增
```sql
SELECT crawl_date AS `采集日期`,
       SUM(CASE WHEN change_pct < -5 THEN 1 ELSE 0 END) AS `降价>5%SKU数`,
       COUNT(*) AS `可比SKU数`
FROM v_price_change
WHERE prev_price IS NOT NULL
GROUP BY crawl_date ORDER BY crawl_date
```
> 阈值 5% 与钉钉告警同口径，这条线往上走 = 降价面在扩大。

## 第 7 章 · 加筛选器：想"选一个商品看走势"时

1. 卡片 SQL 加模板段（`[[ ]]` 内为空时整段忽略）：
```sql
SELECT crawl_date AS `采集日期`, price AS `价格`, sku_name AS `SKU`
FROM v_price_daily
WHERE 1=1 [[AND product_id = {{product_id}}]]
ORDER BY crawl_date
```
2. 问题右上「筛选器」→ 新建变量 `product_id`，类型 Text/Number
3. 看板「添加筛选器」→ 选这个变量 → **卡片右上「筛选器映射」必须把变量对到卡片**
   > 漏映射 = 选了没反应，**不报错**，是最隐蔽的一类失效

## 第 8 章 · 维护：业务变了怎么改

> **决策规则：数字口径变了 → 改视图；只是展示变了 → 改卡片。**

| 诉求 | 动哪里 | 做法 |
|------|--------|------|
| 现有图排序/分档/TOP N 不合适 | 卡片 | UI「编辑查询」；或 `PUT /api/card/:id` 只传 `dataset_query` |
| 要一张新图 | 卡片 | 照 `add_cards.py`：建卡 → PUT 全量 dashcards |
| "降价"等口径要改 | 视图 | 改 `init_bi_views.sql` → 重跑 → Metabase「手动同步」 |
| 加筛选器 | 卡片+看板 | 第 7 章三步，注意映射 |
| 删图/重排 | 看板 | UI 拖；API 传全量 dashcards |

**改完三查**：①API 实跑 `POST /api/card/:id/query` 行数 > 0；②与 ⑤钉钉交叉验证同一批行；③中文/日期轴/图样式肉眼过一遍。

> 真实翻车记录：拼 SQL 少一个空格变成 `NULLGROUP BY`，**建卡成功、图 400**——只验证"卡建出来了"会漏。

## 第 9 章 · 排错速查

| 现象 | 原因 | 解法 |
|------|------|------|
| 启动即 `NoClassDefFoundError: SequencedCollection` | 用了 Java 17 | 换 Java 21+ |
| 开局一片"无法处理此请求" | Metabase 比 MySQL 先起 | 等 MySQL 就绪后「手动同步」或重启 |
| 趋势图点数虚高、均价偏 | 查了原始表没去重 | 一律查 `v_price_daily` |
| 「历史新低」恒为空 | `MIN` 含当日 | `ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING` |
| 「现价」里混着旧商品 | `competitor_sku` 累积表 | `DATE(crawl_time)=最近采集日` 过滤 |
| 中文别名报语法错 | 别名含 `%`/空格/括号 | 反引号包裹 |
| 改视图字段后图报"字段不存在" | 元数据缓存 | 管理→数据库→「手动同步」 |
| `/api/dataset` 全 200 却判失败 | 本版同步查询返回 **HTTP 202** | 判定写 `in (200,202)` |
| `PUT /api/dashboard` 500 ClassCastException | dashcards 字段不全 | 12 字段全给（见第 6 章） |

完整清单：[原理与踩坑 §9](BI看板搭建全流程.md)。

## 第 12 章 · 面试可以怎么讲（STAR 提炼）

- **S**：竞品价格每日靠人工翻页记录，无趋势、无预警
- **T**：把采集数据变成"每天 1 分钟能看完"的决策看板
- **A**：影刀采集 → Python 清洗入库 → 4 视图统一口径 → Metabase 12 图；口径与钉钉告警同源，视图层解决同日多次采集的重复计数；API 脚本化重建，10 分钟可复制一套
- **R**：单次采集 20 商品/数百 SKU 全自动入库；预警从 26 条幽灵收敛到 4 条真实新低；看板与告警口径 100% 一致；整套文档化、可复现

**一个能加分的细节**：主动说清边界——只适配淘宝 PC DOM、单机单账号、H2 配置库不适合生产。比"什么都能做"更可信。
